# ПОС — преподавательская оценка студентов

Домашнее задание №2 по КПО: консольный модуль оценивания с DDD,
Ports and Adapters и тремя паттернами. Python 3.12+, uv, punq;
для проверок — pytest, ruff и mypy.

## Запуск

```text
uv sync --locked
uv run pos
```

В `.python-version` выбран Python 3.14; uv установит его при необходимости.
Команды запуска одинаковы для Windows, Linux и macOS.

Демонстрация полного сценария:

```text
uv run pos scenarios/demo.txt
```

Сценарий добавляет двух студентов и два критерия, выставляет, исправляет и отменяет
оценки, показывает результаты и экспортирует `results.csv` в текущую папку.
Повторный запуск перезаписывает этот файл. Итоги в конце: Анна — 7.70, Иван — 10.00.

**Данные живут в памяти до завершения процесса.** CSV — экспорт ведомости,
а не сохранение состояния для следующего запуска. Импорт и постоянное хранилище
в текущий объём не входят.

## Команды

Идентификаторы задаёт пользователь; имена могут совпадать. Для удобства используйте
идентификаторы без пробелов, например `s1` и `exam`. Аргументы с пробелами заключайте
в двойные кавычки. Дробные числа вводятся через точку.

| Команда | Назначение |
|---|---|
| `student add s1 "Анна Иванова"` | Добавить студента |
| `student list` | Список студентов |
| `criterion add exam "Экзамен" 20 60` | Критерий: максимум 20, вес 60 |
| `criterion list` | Рубрикатор |
| `evaluation set s1 exam 15 "Хорошая работа"` | Выставить оценку; комментарий необязателен |
| `evaluation change s1 exam 18 "Перепроверено"` | Исправить существующую оценку |
| `evaluation remove s1 exam` | Отменить оценку |
| `evaluation list s1` | Оценки студента |
| `total s1 [final\|preliminary]` | Результат студента |
| `report [final\|preliminary]` | Общая ведомость |
| `export "results.csv" [final\|preliminary]` | Экспорт общей ведомости |
| `help`, `exit` | Справка, выход |

Квадратные скобки обозначают необязательный аргумент; вводить их не нужно.
При исправлении комментарий заменяется вместе с баллом; если его не передать,
он станет пустым. Повторное `set` отклоняется: случайно затереть оценку нельзя.

Разбор команд использует `shlex`: `#` вне кавычек начинает комментарий.
Пути Windows заключайте в кавычки или используйте `/`, например `"D:/reports/results.csv"`.
Папка назначения должна существовать. CSV использует UTF-8 с BOM, разделитель `;`,
поля: идентификатор, студент, результат, оценено, всего, режим.
Экспорт сначала пишет временный файл рядом с целевым и затем заменяет целевой файл.

Ошибки ввода не завершают сеанс. В файле сценария выполнение также продолжается,
но процесс возвращает код 1, если встретилась хотя бы одна ошибка. Успешный сценарий
возвращает 0. `exit` прекращает чтение оставшихся команд.

## Правила результата

Для каждого критерия балл находится в диапазоне от нуля до его максимума включительно.
Максимум и вес строго положительны. NaN и бесконечности запрещены.
Веса относительные: 40/60 и 2/3 означают одинаковое распределение.

```text
итог = 10 × сумма((балл / максимум) × вес) / сумма(весов)
```

Например, 8/10 с весом 40 и 15/20 с весом 60 дают 7.70.
Промежуточные вычисления используют Decimal с точностью 50 значащих цифр.
Для вывода и экспорта результат округляется до двух знаков по ROUND_HALF_UP.

- `final` — режим по умолчанию. Требует все оценки. Для отдельного студента
  перечисляет недостающие критерии; в общей ведомости пишет «не рассчитан».
- `preliminary` — пропущенные оценки дают нулевой вклад, их веса остаются в знаменателе.
  Результат подписан как предварительный; рядом указано количество выставленных оценок.
- Пустой рубрикатор не позволяет рассчитать результат ни в одном режиме.
- Выставленный ноль считается оценкой; пропуск — нет.
- Добавление критерия влияет на все последующие расчёты. Ранее полный набор оценок
  становится неполным. Итог не хранится и не может устареть.

Эти правила согласованы для проекта: условие задания не задаёт точную формулу,
шкалу, округление и обработку пропущенных оценок.

## Карта DDD

Единый язык предметной области: Student — студент, Rubric — рубрикатор,
Criterion — критерий, Evaluation — оценка, Score — балл, Weight — вес,
FinalScoreCalculator — расчёт итога. Эти слова используются в модели и сценариях.

| Тип | Классификация | Ответственность |
|---|---|---|
| `Student` | Entity, корень агрегата | Идентификатор, имя, текущие оценки; операции выставления, исправления и отмены |
| `Rubric` | Корень агрегата | Единственный рубрикатор модуля; владеет критериями и проверяет уникальность их идентификаторов |
| `Criterion` | Entity внутри Rubric | Идентификатор отличает критерий от другого с тем же названием; максимум и вес проверяются при создании |
| `Evaluation` | Value Object | Неизменяемый факт оценки по критерию; исправление заменяет значение |
| `Score`, `Weight` | Value Objects | Значения с проверками допустимых чисел, равенство по значению |
| `ScoreResult` | Value Object | Вычисленный результат и полнота оценивания |
| `FinalScoreCalculator` | Domain Service | Объединяет оценки студента, рубрикатор и правило пропущенных оценок |
| `StudentRepository`, `RubricRepository` | Порты репозиториев | Доступ к агрегатам без привязки к способу хранения |

Два студента с одинаковым именем остаются разными сущностями благодаря идентификаторам.
Два `Score(Decimal("8"))` — одинаковые значения. У оценки нет самостоятельного
идентификатора или истории: сейчас важна одна актуальная оценка на критерий.

### Границы агрегатов и инварианты

`Student` владеет оценками, `Rubric` владеет критериями. Отдельных репозиториев оценок
и критериев нет. В текущем модуле один курс, поэтому сущность Course не вводилась.
Рубрикатор имеет единственную роль в модуле и не нуждается в пользовательском идентификаторе.

Коллекции доступны как tuple, вложенные значения и критерии неизменяемы.
Мутации коллекций проходят через операции агрегатов. Подчёркнутые поля — внутренние
детали Python-классов, не публичный способ изменения модели.

`Student.assign_evaluation` и `correct_evaluation` используют фабрику:
она ищет критерий в переданном рубрикаторе и проверяет верхнюю границу балла.
Перед изменением коллекции выполняются все проверки, поэтому неудачная операция
сохраняет прежнюю оценку. Созданный вручную Evaluation нельзя передать агрегату
в обход этого пути. Калькулятор дополнительно проверяет соответствие оценок
переданному рубрикатору.

Изменение и удаление студентов и критериев не реализованы: в задании они необязательны.
Критерий после добавления неизменяем, поэтому снижение максимума не может незаметно
сделать существующие оценки недопустимыми. Добавление поддерживается.

## Архитектура: Ports and Adapters

```text
src/pos/
  domain/       модель, инварианты, фабрика, расчёт и стратегии
  application/  фасад сценариев, порты хранения/экспорта, данные ведомости
  adapters/     консоль, память, CSV и форматирование вывода
  bootstrap.py  DI-контейнер и сборка приложения
  main.py       запуск консоли или файла команд
tests/          домен, сценарии, DI, экспорт, консоль
scenarios/      воспроизводимая демонстрация
```

Зависимости исходного кода: `adapters → application → domain`.
Адаптеры также могут использовать типы домена. Домен зависит только от стандартной
библиотеки Python. Application знает порты, но не реализации памяти или CSV.
`bootstrap.py` находится на внешнем краю и связывает все части.

Поток команды: консоль → GradingFacade → репозиторий → агрегат/Domain Service →
сохранение через порт → представление результата. Репозитории в памяти хранят ссылки
на агрегаты; `save` явно отмечает границу сохранения для будущих адаптеров.
Транзакций и конкурентного доступа в однопоточном консольном модуле нет.

Порты расположены в application: именно сценариям нужны хранение и экспорт.
CSV и пути файлов отсутствуют в домене. DTO ведомости используются на выходе сценариев;
они не заменяют модель, которая сама охраняет инварианты.

## Паттерны

| Группа | Паттерн и место | Задача |
|---|---|---|
| Порождающий | Фабрика — `EvaluationFactory` в domain/evaluations.py | Единый путь создания допустимой оценки при выставлении и исправлении |
| Структурный | Facade — `GradingFacade` в application/facade.py | Скрывает от консоли координацию репозиториев, модели, расчёта и экспорта |
| Поведенческий | Strategy — `MissingEvaluationPolicy` в domain/scoring.py | Подменяет правило допустимости расчёта при пропусках, сохраняя общую взвешенную формулу |

Фабрика — простая фабрика, как в примере задания; это не иерархия GoF Factory Method.
Дополнительные подклассы создателей здесь не нужны.
Фасад одновременно служит прикладным сервисом: отдельные классы-проходники для каждой
команды не создавались. Стратегии реально выбираются через final/preliminary:
FinalScorePolicy требует полноту, PreliminaryScorePolicy разрешает пропуски.
Подсчёт сохраняет веса пропущенных критериев и считает их вклад нулевым.

## DI

`build_container()` в bootstrap.py регистрирует зависимости в punq.
Репозитории имеют по одному экземпляру на приложение, чтобы все сценарии видели
общих студентов и рубрикатор. Фасад, калькулятор, стратегии и экспортёр не содержат
собственного изменяемого состояния и создаются контейнером.

Контейнер используется только при сборке. Фасад получает зависимости через конструктор.
Тест `test_container_shares_repositories_and_allows_exporter_replacement` подменяет
экспортёр через регистрацию и проверяет, что сценарий вызывает новую реализацию.

## Проверки

```text
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run mypy
```

Проверяются границы баллов, неизвестный критерий, неизменность данных при отказе,
исправление и отмена, различие нуля и пропуска, нормализация весов, отсутствие
промежуточного округления, изменение итога при добавлении критерия,
подмена зависимости в DI, CSV с кириллицей и кавычками, восстановление после
ошибок команд, коды завершения и полный запуск демонстрации отдельным процессом.
